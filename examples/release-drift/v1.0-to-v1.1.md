# Release drift example: v1.0 → v1.1

A clean before/after release pair for `my-app`, showing the kind of
version diff VibeRaven's Versions & releases panel produces between two
release snapshots. See
[docs/version-comparison.md](../../docs/version-comparison.md) for what
each diff input means and what counts as "riskier."

## Before: v1.0 (known-good release)

- **Dependencies:** `next@14.2.3`, `@supabase/supabase-js@2.43.0`, `stripe@14.21.0`
- **Schema:** `supabase/migrations/0011_profiles.sql` — `profiles` table with
  RLS enabled, `select`/`insert`/`update` policies scoped to `auth.uid() = id`
- **Env vars:** `.env.example` lists `NEXT_PUBLIC_SUPABASE_URL`,
  `NEXT_PUBLIC_SUPABASE_ANON_KEY`, `STRIPE_SECRET_KEY`,
  `STRIPE_WEBHOOK_SECRET` — all four present and matching in every
  environment (dev, preview, production)
- **Provider config:** Stripe live-mode webhook endpoint points at the
  production URL; signature verification passes

## After: v1.1 (current release)

Three changes shipped since v1.0:

1. `supabase/migrations/0012_profiles_notes.sql` adds an
   `internal_notes` column to `profiles`, for internal team use only.
   The existing `select` policy on `profiles` was not updated, so
   `internal_notes` is exposed to the same `auth.uid() = id` scope as
   every other column — readable by the row's own user, which is not
   what "internal" was supposed to mean.
2. The Stripe webhook signing secret was rotated in the Stripe dashboard
   (Developers → Webhooks) as part of a routine key rotation. The
   `STRIPE_WEBHOOK_SECRET` value in Vercel's Production environment
   variables was not updated to match.
3. `@sentry/nextjs@8.9.2` was added to `package.json` for error
   monitoring, but `NEXT_PUBLIC_SENTRY_DSN` was never added to
   `.env.example` or set in any environment, so the SDK initializes
   without a DSN and silently sends nothing.

## VibeRaven version diff: v1.0 → v1.1

| Category | Evidence | v1.0 | v1.1 | Status |
|----------|----------|------|------|--------|
| Schema | `supabase/migrations/0012_profiles_notes.sql`, `profiles` select policy | ✅ verified | 🔴 blocker | Regression — new column not excluded from the existing select policy |
| Provider config | Stripe dashboard webhook secret vs. Vercel Production `STRIPE_WEBHOOK_SECRET` | ✅ verified | 🔴 blocker | Regression — signature check will reject every event in production |
| Dependencies | `package.json` — `@sentry/nextjs@8.9.2` added | not present | ⚠️ needs action | New and incomplete — added but not wired up |
| Env vars | `.env.example` — `NEXT_PUBLIC_SENTRY_DSN` | not present | ⚠️ needs action | New and incomplete — used implicitly by the new dependency, undocumented |

**Gate status:** `not_clear` — 2 blockers, 2 warnings.

## What a fix looks like

- **Schema (repo-code):** update the `profiles` select policy in a new
  migration to exclude `internal_notes`, or split it into a separate
  table with its own policy.
- **Provider config (dashboard action):** copy the rotated signing secret
  from Stripe → Developers → Webhooks into Vercel → Settings →
  Environment Variables (Production) for `STRIPE_WEBHOOK_SECRET`.
- **Dependency (repo-code):** add `NEXT_PUBLIC_SENTRY_DSN` to
  `.env.example` with a comment on where to find it in the Sentry
  dashboard, and set the real value in each environment.
